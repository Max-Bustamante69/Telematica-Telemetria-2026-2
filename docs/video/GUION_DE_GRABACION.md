# Guion de grabación

Lee únicamente los párrafos de voz. Los títulos sirven para nombrar los archivos y orientarte. El teleprompter de cada integrante es `teleprompter-maximiliano.html` o `teleprompter-valeria.html`, en esta misma carpeta: ábrelo en el navegador, pulsa F para pantalla completa y espacio para que el texto avance solo.

## 01-max-intro.mp4 — Presentación y problema (Maximiliano)

Hola, somos Maximiliano Bustamante y Valeria Hornung, y este es nuestro proyecto de Telemática: una plataforma distribuida de telemetría. El problema es el de una organización con instalaciones en varios lugares, donde cada una tiene sensores que reportan temperatura, humedad, consumo de energía, vibración y el estado de los equipos. Todo eso tiene que llegar a un servidor central en la nube, y un operador tiene que poder consultar cualquier dispositivo y recibir una alerta cuando algo se sale de rango. Lo resolvimos con tres programas. Nodos de telemetría en Python que simulan los sensores. Un servidor central escrito en C, que corre dentro de un contenedor Docker en una instancia de Amazon EC2. Y un cliente operador, también en Python. Los nodos encuentran el servidor por un nombre DNS: telemetria punto digitdeck punto co. Ningún archivo del proyecto contiene la dirección IP.

## 02-max-protocolo.mp4 — El protocolo TLP (Maximiliano)

Diseñamos un protocolo de aplicación propio, de texto, que llamamos TLP, Telemetry Line Protocol. Cada mensaje es una línea terminada en salto de línea, con campos separados por una barra vertical, y el primer campo es el tipo de mensaje. Un nodo se registra con REGISTER, su identificador, su ubicación y la lista de variables, y el servidor responde OK REGISTERED con el puerto UDP. Después el nodo envía TELEMETRY, identificador, número de secuencia, variable y valor, un datagrama por variable. Y el operador consulta con comandos como LIST NODES, GET LAST o GET STATUS; las respuestas de varias líneas terminan con END, para que el cliente sepa dónde acaba la respuesta sin depender del cierre de la conexión. Los errores llevan un código: 100 formato incorrecto, 101 comando desconocido, 102 nodo desconocido, 103 parámetro inválido, 104 nodo no registrado, 105 línea demasiado larga y 106 servidor lleno. La telemetría va por UDP porque cada nodo manda cinco datagramas cada dos segundos, perder uno no importa, y el número de secuencia nos permite contar exactamente cuántos se perdieron. El registro, las consultas y las alertas van por TCP porque necesitan confirmación y orden: una alerta perdida es un incidente que nadie atendió.

## 03-max-servidor.mp4 — El servidor en C (Maximiliano)

El servidor está escrito en C con sockets POSIX. En tcp operator punto c se ve la secuencia completa: socket, bind en el puerto 5001, listen con una cola de dieciséis, y accept en un bucle. Cada conexión aceptada recibe su propio hilo con pthread create, y el hilo acumula bytes hasta encontrar el salto de línea, porque TCP es un flujo y un comando puede llegar partido en dos lecturas o dos comandos en una sola. En udp telemetry punto c está el otro socket: recvfrom en el puerto 5000 devuelve el datagrama y la dirección del nodo, y sendto responde a esa misma dirección solo cuando el nodo no está registrado. Todo el estado, los nodos, las últimas mediciones y las alertas, vive en una estructura protegida por un mutex. Ignoramos SIGPIPE para que un operador que cierre a mitad de una respuesta no mate el proceso, y al recibir SIGTERM llamamos shutdown sobre los sockets de escucha para que los hilos bloqueados despierten y el servidor termine limpio. El binario corre en Docker, y aquí está docker ps en la instancia: el contenedor lleva horas arriba y el healthcheck dice healthy.

## 04-max-nube.mp4 — Nube, DNS y Docker (Maximiliano)

El servidor está desplegado en una instancia t3 micro de Amazon EC2 en la región de Virginia del Norte, con Ubuntu 24.04. El grupo de seguridad abre exactamente cuatro puertos: 22 TCP para administración, 5000 UDP para telemetría, 5001 TCP para registro y operadores, y 8080 TCP para la interfaz web. La instancia tiene una IP elástica, 100 punto 25 punto 236 punto 127, para que no cambie si se reinicia. En Cloudflare, el registro A telemetria apunta a esa IP con el proxy desactivado, porque el proxy de Cloudflare solo reenvía HTTP y bloquearía UDP y el puerto 5001. Aquí hago nslookup en vivo: telemetria punto digitdeck punto co resuelve a 100 punto 25 punto 236 punto 127. El código se envía a la instancia con git archive por SSH, porque el repositorio es privado, y se construye allí con docker compose: una imagen de dos etapas, gcc para compilar y Debian slim para ejecutar, que pesa 114 megabytes.

## 05-val-nodos.mp4 — Los nodos de telemetría (Valeria)

Los nodos están escritos en Python. Cada nodo tiene un identificador único, simula cinco variables y, antes de nada, resuelve el nombre del servidor con getaddrinfo: la primera línea de salida siempre muestra el nombre y la IP que obtuvo. Luego se registra por TCP con REGISTER y espera el OK REGISTERED. A partir de ahí envía por UDP cinco datagramas cada dos segundos, uno por variable, con un número de secuencia que crece de uno en uno. Si el servidor se reinicia y pierde el registro, responde NACK 104 por UDP, y el nodo se vuelve a registrar solo, sin intervención. Aquí lanzo cinco nodos al mismo tiempo desde mi equipo, NODE01 a NODE05, y en la interfaz web del servidor aparecen los cinco en estado ACTIVE, con el contador de datagramas recibidos subiendo y cero perdidos.

## 06-val-operador.mp4 — El cliente operador y las alertas (Valeria)

El cliente operador se conecta por TCP al puerto 5001. Con LIST NODES veo todos los nodos registrados, su ubicación, si están activos y cuántos datagramas ha recibido y perdido cada uno. Con GET LAST y un identificador veo las últimas mediciones de ese nodo, y con GET STATUS su estado. SYSTEM STATUS resume el servidor: tiempo activo, nodos, operadores conectados y contadores de UDP y TCP. Si escribo un comando que no existe, el servidor responde error 101, y si pregunto por un nodo que no existe, error 102: la conexión sigue viva. Ahora me suscribo a las alertas con SUBSCRIBE ALERTS y, en otra terminal, lanzo un nodo con la opción force alert TEMP, que manda temperaturas por encima de 40 grados. La alerta TEMP HIGH llega sola al operador por la misma conexión TCP, y aparece también en GET ALERTS y en la tabla de alertas de la web.

## 07-val-fallos.mp4 — Recuperación ante fallos y pruebas (Valeria)

Ahora las pruebas de recuperación. Con los nodos enviando, reinicio el contenedor por SSH con docker restart. El nodo recibe cinco NACK 104, uno por cada variable del ciclo, envía REGISTER otra vez, recibe OK REGISTERED y sigue con la telemetría: once segundos entre el reinicio y el reregistro, sin tocar nada. Si detengo un nodo con control C, manda BYE por TCP y en LIST NODES pasa a INACTIVE. También le enviamos datagramas basura y una línea de 700 bytes por TCP: el servidor los cuenta como inválidos y sigue respondiendo. Todo esto está automatizado en tests e2e punto sh, que corre veinte comprobaciones contra el servidor en la nube: todas en verde. Y la prueba de conteo: loss test envía 500 datagramas numerados a 478 por segundo desde Medellín hasta Virginia; el servidor recibió los 500 y no detectó ningún hueco en la secuencia.

## 08-val-wireshark.mp4 — Análisis de tráfico con Wireshark (Valeria)

Esta captura se tomó en mi equipo mientras un nodo y un operador hablaban con el servidor en la nube. Con el filtro udp punto port igual 5000 veo un datagrama de telemetría: IP de origen privada 192 punto 168 punto 58 punto 130, destino 100 punto 25 punto 236 punto 127, puerto de origen efímero 49921, puerto destino 5000, longitud UDP 37, que son 8 bytes de cabecera más 29 de datos, y en los bytes se lee el texto TELEMETRY NODE12 1 TEMP 24 punto 5. No hay conexión ni confirmación: el primer paquete ya lleva datos. Con tcp punto stream igual 1 está la conexión del operador: SYN, SYN ACK y ACK, el saludo de tres vías, con 85 milisegundos entre el SYN y el SYN ACK, que es la ida y vuelta hasta Virginia. Después el segmento PSH ACK con GET LAST, el ACK del servidor confirmando 16 bytes, la respuesta de 160 bytes, QUIT, OK BYE y el cierre con FIN. Y con el filtro de DNS está la consulta A y la respuesta con la IP y un TTL de 260 segundos. En resumen: el mensaje TLP es la carga de aplicación; UDP o TCP añaden los puertos, y TCP además secuencia y confirmación; e IP añade las direcciones que cruzan Internet hasta la instancia.
